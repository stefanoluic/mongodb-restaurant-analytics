# V2 materialized analytics

V2 consists of four derived collections built from V1. It stores aggregate statistics for a fixed analytical workload, rather than copies of individual restaurant records. The V1 collections remain the source of truth.

## Collections and grain

| Collection | One document represents | Query consumers |
| --- | --- | --- |
| `city_offer_stats` | Country + city | q01, q02, q03, q04, q07 |
| `city_cuisine_stats` | Country + city + cuisine in a major tourist city | q05, q06 |
| `classification_signal_stats` | Feature + scope, or tag + price segment | q08, q09 |
| `cuisine_quality_stats` | Cuisine | q10 |

City/cuisine keys include the country so identically named cities in different countries remain separate. String IDs combine those identity parts with `||`; the source is assumed not to contain that separator in identity values. The query outputs use the individual identity fields.

The list of major tourist cities is defined in `src/v1_queries.py` and shared by the builder.

## General statistics and query populations

The builder retains general descriptive statistics alongside query-specific measures. Averages must be calculated over the same population as their associated counts.

### city_offer_stats

General fields include `total_restaurants`, `rated_restaurants`, city rating/review averages, price counts, dietary counts and meal availability.

Query-specific measures include:

- q01: `diet_friendly_high_rated_count`, `diet_friendly_avg_rating` and dietary/review breakdowns.
- q02: `gluten_free_high_rated_count` and rating/review averages.
- q03: `affordable_lunch_dinner_count`, `avg_value_for_money` and rating/review averages.
- q04: `expensive_food_service_gap_count`, `expensive_avg_gap` and `expensive_avg_value`.
- q07: `quality_demand_count`, `premium_share`, premium counts and averages.

See the pipelines for exact rating, review and minimum group-size thresholds.

### city_cuisine_stats

General fields include restaurant counts and rating/review averages. `tourism_*` fields use q05's eligible population; `investor_*` fields use q06's population. City totals are retained alongside cuisine statistics.

### classification_signal_stats

Common fields include `signal_type`, `signal_value`, `scope`, `total_restaurant_count`, `rated_restaurant_count`, `avg_rating` and `avg_reviews`.

For q08/q09, a **successful** restaurant has rating >= 4.5 and at least 100 reviews. q08 additionally restricts locations to the configured major tourist cities. q09 requires a known price segment.

| Field | Population |
| --- | --- |
| `successful_restaurant_count` | Successful restaurants in this signal group |
| `successful_avg_rating`, `successful_avg_reviews` | That same successful population |
| `successful_avg_value_rating` | q08: successful restaurants with a value rating |
| `successful_city_count` | q08: distinct non-null cities among successful restaurants |
| `successful_avg_price_score` | q09: successful restaurants in the price segment |
| `avg_rating`, `avg_reviews`, `city_count`, other general fields | The wider signal population, before the success filter |

q08/q09 project the successful averages into their public output fields `avg_rating`, `avg_reviews`, etc. The general averages are retained for other exploration but are not substituted into these queries.

### cuisine_quality_stats

General measures cover the whole cuisine group. q10's **qualified** population requires at least 100 reviews and a non-null excellent-review count.

- `restaurant_count`: qualified count.
- `qualified_avg_rating`, `qualified_avg_reviews`: qualified averages.
- `qualified_avg_excellent_ratio`: mean of each qualified restaurant's excellent-review count divided by its total review count.

This is an **unweighted mean of restaurant-level ratios**, not the ratio of summed review counts. q10 projects the qualified fields as `avg_rating`, `avg_reviews` and `avg_excellent_ratio`.

## Indexes

Compound indexes follow the ranking keys below. City/cuisine identity fields provide a deterministic final tie-breaker; q08 uses `signal_value`, q09 uses `signal_value` + `price_segment`, and q10 uses `cuisine`.

| Index | Leading fields, in order |
| --- | --- |
| `q01_diet_city_rank` | diet count DESC, diet average rating DESC |
| `q02_gluten_city_rank` | gluten-free count DESC, gluten-free average rating DESC |
| `q03_value_city_rank` | value average DESC, affordable count DESC |
| `q04_gap_city_rank` | expensive gap DESC, expensive value ASC, expensive count DESC |
| `q05_city_cuisine_rank` | tourism count DESC, tourism average rating DESC |
| `q06_underrepresented_rank` | investor average rating DESC, investor average reviews DESC |
| `q07_premium_city_rank` | quality demand count DESC, premium share ASC, premium average rating DESC |
| `q08_signal_feature_rank` | signal_type ASC, scope ASC, successful count DESC, successful average rating DESC |
| `q09_signal_tag_price_rank` | signal_type ASC, successful count DESC, successful average rating DESC |
| `q10_cuisine_quality_rank` | qualified excellent ratio DESC, qualified count DESC |

The complete definitions are in `create_indexes()` in `src/build_v2.py`. The benchmark records the actual database indexes and winning execution plans; adding an index does not guarantee that MongoDB will choose it for every query.

## Build and refresh

`python src/build_v2.py` creates all four collections and their indexes, recording elapsed time and source/materialized counts. Existing populated derived collections require `--replace`. V1 is preserved.

The build moves expensive joins, unwinds and groups out of the read path. Fast reads come at the cost of build time, extra storage and stale results until the next rebuild. Rebuild after changing V1. Refreshes are full, non-atomic replacements intended for an offline analytical workflow. Do not serve concurrent readers during a rebuild.
